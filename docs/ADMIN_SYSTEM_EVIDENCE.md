# System and maintenance evidence

Reviewed target: **Speedport Smart 4R Typ A, 010152.5.0.001.0**. These are implementation contracts from saved firmware JavaScript, sanitized HTML structure/validators, and the official manual. Offline fixtures prove integration behavior; they do **not** claim a successful live router write. No reset, firmware installation, credential change, upload, or other maintenance action was performed for this work.

Maintenance availability means the exact firmware and administrator execution path are eligible **to attempt preflight**. It does not invent persistent `maintenance_*` discovery capabilities. Every declared endpoint/referer is freshly read and checked before the single POST. The existing hub owns administrator authorization, locking, rate limits and cleanup. Reconnect outcomes invalidate protected caches and outstanding edits; they skip eager state refresh. Unconfirmed session cleanup cannot produce a successful result. No maintenance result contains identifiers, addresses, credentials, telephone numbers or log text.

## Private file-transfer implementation

The native file forms are separate from encrypted JSON commands. The backup-download GET form contains `addTokenField()`, which inserts `_tn`; the restore, router-firmware and mesh-firmware multipart POST forms contain neither this call nor a token input. Their authenticated session cookies remain required. No `httoken`, CCM body, unreviewed filename convention or automatic redirect is invented for these upload forms.

The Home Assistant prepare endpoint issues a 120-second, one-use approval bound to the server-owned administrator, refresh-token identity, loaded entry, exact action, typed confirmation, byte length and SHA-256 digest. The execute endpoint accepts one bounded metadata part and, for uploads, one binary file part. All bytes stay in memory; there is one process-wide active transfer slot, no disk spool and no base64 WebSocket payload. The server checks the complete body length and digest before any router POST, then rechecks identity, lifecycle, fresh firmware and authenticated page readiness under the existing locks. Native transfer fields are fixed, all writes are single-shot, and request/error values are never logged or echoed.

Downloads use a Home Assistant POST body for the optional backup password; only the backend router GET contains `save_pwd` and `_tn`. Empty backup passwords are permitted by the firmware; nonempty export passwords require 8–255 characters from its exact `CharsForPwd` alphabet. Restore passwords use the native 255-character bound. HTTP provides no transport encryption beyond any encryption inside the file itself; this is stated in the editor warning. Responses must be bounded, nonempty attachments rather than login/error pages, and session cleanup must succeed before the private file is released with a fixed filename and no-store headers. The integration's download bound is the reviewed 6,291,456-byte restore limit, not an assertion about every possible firmware export.

Only exact expected same-origin redirect pages and reviewed status values are classified, without following the redirect. Restore `status=ok` and router firmware `status=ok`/`firmware_status=ok` require recovery; they never prove the restored configuration or installed version. Router firmware `status=wait` permits four bounded `FirmwareUpdateCheck.json` reads. Mesh `status=wait` only starts the firmware UI's countdown and remains unverified. Unknown responses, transport failures and cancelled upload attempts invalidate protected state and outstanding approvals; no upload is retried. Official image compatibility, backup restorability and successful live roundtrips remain user-authorized validation, not claims from offline fixtures.

## Private router-password implementation

The password editor is implemented through a dedicated transaction, not the generic settings POST path. A private revision binds the exact model, firmware and fresh router serial to the administrator and HA refresh-token session for 120 seconds. Three password fields are always empty on read. Exact typed confirmation and a recovery attestation are required; the old password permits 1–32 characters and the repeated new password 8–32, using the captured firmware alphabet. Masked, mismatched and unchanged credentials are rejected.

The owner releases its existing login and holds the hub/client locks. Separate fresh HTTP sessions and cookie jars authenticate the entered old password and, only after exact `status=ok` plus `login=success`, the new password. One password-changing POST sends the native plaintext form fields inside the session's encrypted JSON transport. It is not normal-login challenge hashing. Both login and password-change success responses must authenticate with the corresponding challenge key. Missing/ambiguous ACKs never trigger a new-password attempt, credential cycling, redirects or another change POST.

Only an independent new-password login on the same fresh serial-bearing router can produce a private, one-use persistence proof. HA stores that proven credential and bridges it into the active client; passwords never enter public results, diagnostics, entity state or Recorder. A failed final logout can still leave the credential proven and safely stored, but the result remains `outcome_unknown/session_cleanup_failed`, not verified. Cancellation, unknown outcomes and failed persistence latch protected access off for the current hub, invalidate other drafts and request HA reauthentication. Cleanup failures and manual retry/inventory buttons cannot clear that latch. Public status and WAN polling continue. A new runtime after credential update/reload starts normal session ownership checks again. No Keychain password is modified, and no live credential change was performed for validation.
